\# SmartPay API Collection



Bruno API request collection for testing the SmartPay Malawi backend locally.



\- \*\*Backend repository:\*\* \[SmartPay-Malawi](https://github.com/KelvinJustin/SmartPay-Malawi)

\- \*\*API collection:\*\* \[SmartPayAPI-Collection](https://github.com/KelvinJustin/SmartPayAPI-Collection)



\## What's Included



| Folder | Description |

|---|---|

| `authentication/` | Merchant registration, login, OTP verification, email verification, session checks, logout, and account deletion |

| `merchants/` | Retrieve, update, and submit merchant profiles for review |

| `admin Authentication/` | Admin login, session checks, and logout |

| `admin/` | Retrieve merchant applications, start reviews, approve applications, and reject applications |

| `environments/` | Bruno environment configuration |



The collection documents the requests currently available in this repository. Payment transaction and provider-integration requests can be added as those backend features are implemented.



\## Requirements



\- \[Bruno](https://www.usebruno.com/)

\- The \[SmartPay-Malawi backend](https://github.com/KelvinJustin/SmartPay-Malawi)

\- A configured development database

\- Development merchant and admin accounts for authenticated requests



\## Getting Started



1\. Clone the collection:



&#x20;  ```bash

&#x20;  git clone https://github.com/KelvinJustin/SmartPayAPI-Collection.git

&#x20;  ```



2\. Start the backend using the setup instructions in the \[main repository](https://github.com/KelvinJustin/SmartPay-Malawi).



3\. Open Bruno and open the cloned `SmartPayAPI-Collection` directory as a collection.



4\. Select the \*\*Smartpay\*\* environment.



5\. Check the `baseUrl` variable. It defaults to:



&#x20;  ```text

&#x20;  http://localhost:3000

&#x20;  ```



&#x20;  Change it if your backend runs on a different host or port. Requests already include the `/v1` API prefix.



6\. Replace example request values with valid development account details and test data.



7\. Run the requests in the appropriate order.



\## Suggested Request Order



\### 1. Merchant Authentication



1\. \*\*Register\*\* — create a development merchant account.

2\. \*\*Verify Email\*\* — submit the OTP delivered by the configured email service.

3\. \*\*Login\*\* — initiate login using the merchant's credentials.

4\. \*\*Verify Login (OTP)\*\* — submit the login OTP when required.

5\. \*\*Auto Login\*\* — call `GET /v1/auth/me` to check the authenticated session.

6\. \*\*Logout\*\* — end the merchant session.



Use OTPs generated by your actual development environment. Values included in sample request bodies are examples only.



\### 2. Merchant Profile



After signing in as a merchant:



1\. \*\*Profile\*\* — retrieve the current merchant profile.

2\. \*\*Update Profile\*\* — update the required onboarding fields.

3\. \*\*Submit Profile for Review\*\* — submit the completed profile for admin review.



\### 3. Admin Application Review



1\. \*\*Admin Login\*\* — sign in using a provisioned development admin account.

2\. \*\*Admin Auto Login\*\* — check the admin session.

3\. \*\*Get merchant application\*\* — list merchant applications.

4\. Set the `profileId` variable to a valid merchant profile ID from the development database.

5\. \*\*Start review\*\* — move an eligible application into review.

6\. \*\*Approve application\*\* or \*\*Reject application\*\* — test the appropriate review outcome.

7\. \*\*Admin Logout\*\* — end the admin session.



Admin accounts are provisioned separately; the collection does not create admin accounts.



\## Authentication and Cookies



The backend uses cookie-based sessions for authentication.



\- Sign in and complete OTP verification before sending requests that require authentication.

\- Ensure Bruno retains and sends the authentication cookies.

\- Merchant and admin sessions use separate cookies. A merchant session should not be assumed to authenticate admin requests.



\## Troubleshooting



| Problem | What to check |

|---|---|

| Connection refused or timeout | Confirm the backend is running and `baseUrl` is correct. |

| `404 Not Found` | Check the endpoint path and `/v1` prefix. |

| `401 Unauthorized` | Sign in through the correct authentication flow, complete OTP verification if required, and check cookie handling. |

| `400 Bad Request` | Verify the request body, required fields, and OTP format. |

| Application not found or invalid state | Use a valid profile ID and follow the application review transitions. |

| Email OTP not received | Check the backend email configuration and provider logs or inbox. |



\## Safety Notes



\- Use development data and non-production credentials.

\- Never commit real passwords, OTPs, session cookies, API keys, or personal customer data.

\- Treat destructive requests such as \*\*Delete Account\*\* as potentially irreversible.

\- Only test live payment activity when the environment and authorization explicitly permit it.
